Under the Hood

How this server is built.

What This Is

Everything on this site is served by a web server written from scratch in C++98, with no libraries and no borrowed parts. A web server is a program that waits for browsers to connect, reads what they ask for, and sends back an answer. This page explains how ours is put together.

One Worker, Many Visitors

The whole server is a single program running a single thread of work. It does not hire a worker per visitor. Instead it behaves like a chess master playing forty boards at once: it keeps a list of every open connection, asks the operating system which of them needs attention right now, deals with each of those in one small step, and then asks again. That question is a system call named poll(), and the endless ask-and-serve cycle is called the event loop. It is the heart of the program; everything else is machinery the loop calls on.

For this to work, one rule is absolute: no step is ever allowed to stop and wait for a single visitor. If the server paused to wait for one slow phone connection, every other visitor would freeze with it. So every operation is set up to either finish immediately or politely say "not yet", in which case the loop simply moves on and comes back later.

The Life of One Request

When your browser connects, the server accepts the call and creates a small record for it: which connection this is, what has arrived so far, what stage the conversation is at. Then the bytes of your request start arriving, and here is a truth about networks that shapes the whole design: data does not arrive in tidy wholes. A request may come in one piece or in fifty fragments. The server's parser reads whatever fragment has arrived, remembers exactly where it left off, and continues when the next fragment comes. No fragment is ever read twice, and nobody waits.

Once the request is complete, the server decides what it means. It looks the requested path up in its configuration, which works like a routing table: the most specific matching rule wins, and that rule says what is allowed here and where the real files live. Then the answer is prepared, whether that is a file read from disk, a folder listing generated on the spot, or the output of a script. Sending it back follows the same fragmented rhythm as reading: the server writes as much as the connection will take right now, remembers its place, and finishes on later turns of the loop. Afterwards the connection usually stays open, ready for your next click without the cost of a new call.

Scripts Are Separate Little Programs

Some pages cannot be files because their content changes: the fortune is different every time, and the uploads listing reflects whatever is on disk right now. For these, the server starts a small external program, hands it the request, and uses the program's output as the response. The mechanism is called CGI, and it is the same idea that powered the early web.

The important design point is isolation. The script runs as its own separate process, connected to the server by two thin channels, one carrying the request in, one carrying the answer out, and those channels are watched by the same loop that watches every visitor. A script that misbehaves cannot drag the server down with it: each one gets a deadline, and one that overruns is killed and answered with an error page while every other visitor carries on. There is a script on this site, slow.py, that hangs on purpose so you can watch exactly that happen.

Behaviour Lives in a Settings File

Nothing about what this server serves is written into the code. A single configuration file declares it all: which folders are public, which actions each part of the site allows, how large an upload may be, which page a visitor sees on each kind of error, and where old links should forward. Change the file, restart, and the same program serves a different site.

The file can even declare several websites at once. This site lives on port 8080, and a second, separate site lives on port 8081, each with its own folders and its own rules, yet both are served by the same single process and the same loop. That is how real servers host many sites on one machine.

Built to Take a Punch

A server lives on the open network, so it must assume visitors who are careless, broken, or hostile. A request that makes no sense is answered with an error, never obeyed halfway: the previous version of this server could be killed outright by a single malformed upload request, and this one answers that same request with a polite 400. An upload that exceeds its size limit is refused while it is still arriving, so nobody can flood the server's memory. A connection that goes silent is closed after a timeout, so abandoned visits cannot pile up. Filenames that arrive from strangers are cleaned before they touch the disk, so a name like ../../secret cannot climb out of the upload folder. And every failure gets a themed page of its own, so even going wrong stays in style: see the 404 page.

From a Terminal

Upload a file, fetch it back, then delete it:

curl -F "file=@notes.txt" http://127.0.0.1:8080/uploads/
curl http://127.0.0.1:8080/uploads/notes.txt
curl -X DELETE http://127.0.0.1:8080/uploads/notes.txt

Watch the server work while you browse:

WEBSERV_LOG=debug ./webserv conf/default.conf

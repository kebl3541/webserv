Under the Hood

One process, one thread, one poll() loop.

What This Is

A web server written from scratch in C++98: no libraries and no borrowed parts. One program, one thread, juggling every visitor at once by never stopping to wait for any of them. Every page on this site comes through it, and each claim below tells you how to see it for yourself.

The Claims, and the Proof

It tells browsers what kind of file it is sending
Every reply carries a label saying "this is HTML", "this is an image", and so on. The old server guessed the label by peeking at the file's first bytes. Images can be recognised that way, but a stylesheet is just text, so CSS got labelled "plain text" and browsers refused to apply it: the whole site showed up bare. This server looks the label up from the file's extension instead. /files/ holds one file of each kind to check this with, and the simplest proof is the page you are reading: if the site is red and gold, the labels are right.
It can take in files two different ways
When you upload a file, the browser wraps it in an envelope format, and someone has to open the envelope. On the Upload Jam page the server opens it itself: it finds the file inside, cleans up the filename so nobody can smuggle in a path like ../../secret, and saves it. On the front page's Dynamic Upload, the server instead passes the sealed envelope to a small Python program that opens it. Same file either way; two different parts of the server doing the work.
Deleting is a real request, not a trick
Web requests come in kinds: GET fetches a page, POST sends data, DELETE removes something. A plain HTML form can only send the first two, which is why the original site's delete page never worked, its form was shouting into a void. The Delete Zone uses a line of JavaScript to send an actual DELETE, and the server removes the file and answers "done". Watch /uploads/ shrink to match.
A stuck script cannot freeze the site
Dynamic pages, the fortune, the uploads listing, are separate little programs the server starts on demand. If one hangs forever, the server gives it a deadline, kills it when the deadline passes, and answers with an error page, while every other visitor sails on unaffected. env.py shows the information a script is handed; status.py shows a script choosing its own response code and the server respecting it.
It does not eat cookies
A reply can set several cookies, one header line each, and those lines must not be squashed together. The easy way to store headers, one slot per header name, keeps only the last line, so one cookie silently vanishes; that was a real bug here once. The Cookie Jar fetches a script that sets two cookies and shows both made the trip.
Where things live is settings, not code
One configuration file decides which folders are served, what is forbidden, where old links redirect, and which page a visitor sees on an error. /docs/ is a folder that does not exist under that name on disk, the config maps it; /old-page forwards you home because one line says so; /nothing-here shows the themed 404 page the config names. Even port 8081 is just a second block in the same file, served by the same single process.

From a Terminal

Upload a file, fetch it back, then delete it:

curl -F "file=@notes.txt" http://127.0.0.1:8080/uploads/
curl http://127.0.0.1:8080/uploads/notes.txt
curl -X DELETE http://127.0.0.1:8080/uploads/notes.txt

Send a body in chunks; the server reassembles it before the script sees it, because CGI has no way to express chunked input:

curl -H "Transfer-Encoding: chunked" -d hello \
     http://127.0.0.1:8080/cgi-bin/echo.py

Watch it work while you poke at it:

WEBSERV_LOG=debug ./webserv conf/default.conf

Fine Print

A request that trickles in over fifty network packets costs no more to read than one arriving whole, and a reply interrupted halfway picks up where it left off. The full routing rules and the deliberate limits are in the README; the audit of the original implementation, every bug with its cause, is in AUDIT.md.
